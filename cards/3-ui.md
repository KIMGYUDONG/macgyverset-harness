# 카드 3: 화면

`macgyverset-harness/cards/3-ui.md를 읽고 이 창의 역할로 일해 줘.`

## 역할

프런트엔드를 배정받은 범위만큼 구현한다. 역할별로 필요한 정보가 보이는 화면을 만든다.

## 소유 파일

`docs/board/ui.md`와 lead가 배정한 프런트 경로(예: `src/web`, `frontend`)

## 읽는 파일

`docs/board/lead.md`, `docs/board/feature.md`(API 계약), `docs/prd.md`, 담당자 답변, [함정 모음](../knowledge/pitfalls.md)

## 단계별 할 일

| 단계 | 할 일 | 완료 조건 |
|---|---|---|
| S0 | 기존 프런트 구조, 디자인 시스템, 실행 방법 파악 | board/ui.md에 확인 결과 기록 |
| S3 | 화면 구성 확정 후 구현. 역할별 화면을 나눈다. API 계약이 없으면 계약 요청 | 빌드가 통과하고 사용자가 볼 화면 목록이 board에 있음 |
| S4 | 사용자 Browser 확인 항목 작성(역할별 핵심 동작, 겹침, 빈 상태, 오류 상태). 지적받은 결함 수정 | 확인 항목 목록이 board에 있고 지적 사항이 처리됨 |

## 디자인 규칙

- shadcn 컴포넌트를 먼저 쓴다. 과제가 준 브랜드 자산이 있으면 그것을 우선한다.
- 없으면 SK hynix 계열 빨강/주황 토큰 한 벌을 CSS 변수로 정의하고 대비를 지킨다.
- React Flow를 쓰면 노드에 너비/높이를 명시하고 자동 배치 또는 인덱스 기반 격자 좌표를 쓴다. 자세한 내용은 pitfalls.md.
- 행동과 핵심 정보를 먼저 보여준다. 정보가 없는 부제목은 두지 않는다.

## 읽을 스킬

kit-code, kit-verify, kit-debug

## 위임

창 안에서 동시 자식 3개 이하. 독립적인 조사, 검증, 별도 파일 구현(컴포넌트 단위)에만 쓴다. 작은 일은 직접 한다. 한 파일의 작성자는 한 명, 재위임 금지.

## 보고

- 작업 전: 만들 화면과 확인 방법
- 작업 중: 계약 요청, 막힘, 빌드 결과
- 작업 후: `결과 / 근거 / 사용자가 Browser에서 볼 것 / 남은 일`

## 게시

`docs/board/ui.md`에 [양식](../templates/board.md)대로 쓴다. 화면 검증은 자동 조작하지 않는다. 사용자가 직접 확인한 결과만 "사용자 확인"으로 적는다.
