# 개발 원칙

개인 개발 지식에서 추린 정적 파생본이다. 실시간 DB 조회나 원본 파일 검증을 수행한 것으로 간주하지 않는다. 과제의 제약과 제공 환경을 우선하고 다음 조건에 맞는 원칙을 적용한다.

1. **백엔드 동작 변경:** 의미 있는 기능 추가와 버그 수정은 실제 실패를 재현하는 테스트부터 시작한다. 문서, 단순 설정과 되돌리기 쉬운 저위험 변경은 불필요한 TDD를 강제하지 않는다.
2. **화면 개발:** 먼저 기존 디자인 시스템을 확인한다. 없으면 색상, 글자, 간격과 기본 상태를 짧게 정한 뒤 화면을 만든다.
3. **화면 구현:** 사용 가능한 기존 컴포넌트를 import해 재사용한다. 필요한 기능과 환경에 맞는지 확인하고 새 의존성은 최소화한다.
4. **서비스 용어:** 실제 서비스에서 사용하는 익숙한 용어를 선택한다. 임의로 만든 표현을 업계 표준처럼 설명하지 않는다.
5. **화면 구성:** 역할이 겹치는 부제목을 최소화하고 사용자가 해야 할 행동과 핵심 정보를 먼저 보여준다.
6. **기능 개발 후 검증:** 실제 실행 계약에 맞는 dev 환경에서 핵심 흐름을 끝까지 검증한다. 시험에서 UI 자동 조작이 금지되면 CLI/API 통합 확인과 사용자의 수동 UI 확인을 조합한다. 이를 자동화된 브라우저 E2E 통과로 표현하지 않는다. 확인하지 못한 운영 동등성은 기록한다.
7. **기존 기능 보호:** 변경의 영향을 받을 정상 경로와 오류 경계를 골라 회귀를 검증한다.
8. **빌드와 테스트:** 변경과 수용 기준에 필요한 검사만 실행한다. 생성물을 늘리거나 같은 검사를 이유 없이 반복하지 않으며, 이 원칙으로 필요한 검증을 생략하지 않는다.
