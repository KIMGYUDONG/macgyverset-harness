# 단계 게이트

시간표는 없다. 각 단계는 완료 조건과 건너뛰기 조건만 가진다. 시험 시간은 고정이므로 아래 원칙으로 줄인다.

- 필요한 작업만 한다. 건너뛴 문서와 단계는 이유를 한 줄 남긴다.
- 핵심 경로(필수 흐름이 끝까지 동작)를 먼저 끝낸다.
- 서술형까지 포함해 종료 시각 안에 끝낸다.
- 종료가 가까워지면 새 기능을 만들지 않는다.

창 카드는 [cards](../cards/README.md). 모든 창은 단계 시작과 막힐 때 `docs/board/lead.md`를 다시 읽는다.

| 단계 | 담당 창 | 할 일 | 완료 조건 | 건너뛰기 조건 |
|---|---|---|---|---|
| S0 설치와 파악 | 전체(1이 정리) | START.md대로 설치. 과제 루트, 기존 시스템, 실행/테스트 방법 파악 | 각 창 board에 실행 명령 기록. lead.md에 과제 요약 | 없음 |
| S1 문제 정의와 담당자 질문 | 1 | kit-define, 데이터가 있으면 kit-data. 질문 목록을 사용자에게 전달, 답을 lead.md에 기록 | 문제 정의와 질문 답변이 lead.md/problem-definition.md에 있음 | 과제 안내만으로 입력/출력/규칙이 모두 명확하면 질문 생략 |
| S2 필요한 문서 | 1 | PRD, ADR, 엣지 케이스, 최적화 중 필요한 것만 한 쪽으로 작성. 기술 스택 확정 | 쓰는 문서 완성. 스택과 창별 배정이 lead.md에 있음 | 문서별로 판단. 기존 시스템에 작은 변경이면 PRD만 또는 전부 생략 |
| S3 병렬 구현 | 2, 3, 5 (4는 시나리오 준비) | 배정대로 구현. 2는 API 계약을 먼저 공개. 5는 실행과 접근 확보 | 핵심 경로가 로컬에서 끝까지 동작. 단위 테스트 통과. URL 기록 | 화면이 없는 과제면 3 생략. 단일 기능이면 창 수를 줄임 |
| S4 테스트 | 4(2, 3, 5가 수정 대응) | 시나리오/경계, API E2E, 부하. 결함은 담당 창에 요청. 사용자 Browser 확인 | 시나리오별 결과 수치가 board/test.md에 있음. 사용자 화면 확인 완료 | 부하 요구가 없는 과제면 부하 생략. E2E는 핵심 흐름이 하나뿐이면 단위 테스트로 갈음하고 이유 기록 |
| S5 매뉴얼과 제출 | 5(1이 최종 판단) | kit-manual로 매뉴얼 3종. kit-finish로 점검. 사용자가 제출 | 매뉴얼의 명령을 실제로 실행해 확인. 제출 점검 결과 기록 | 과제가 요구하지 않은 매뉴얼은 만들지 않음. 심사 에이전트용 안내는 평가에 실행 검증이 있으면 유지 |

## 단일 터미널 대체

창이 하나면 같은 단계를 순서대로 한 창에서 수행한다. board는 `docs/board/lead.md` 하나만 쓰고 항목에 창 이름(기능/화면/테스트/실행)을 붙인다. 단계 사이에 완료 조건만 확인하고 넘어간다. 독립 조사와 검증만 자식에게 맡긴다.

## 단계 전환 확인

- 완료 조건의 근거(명령, 출력)가 board에 있는가
- 다음 단계 입력(배정, API 계약, URL)이 준비됐는가
- 남은 시간 안에 핵심 경로가 가능한가. 아니면 범위를 줄인다.
